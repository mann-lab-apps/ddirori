# 띠로리 스코어 유입 개선 백로그

최종 갱신: 2026-11-27. 악보앱의 다운로드를 늘리기 위해 가장 쉬운 유입 개선부터 한 가지씩 시도한다.

## 목표와 운영 방식

- 핵심 지표: App Store Connect 최초 다운로드 **3 → 5건**.
- 보조 마일스톤: App Store Connect 노출 **32 → 100회**. 기존 화면의 기간 길이와 국가 필터를 확인하고 같은 조건으로 비교한다.
- 웹 방문과 검색 노출은 원인을 파악하는 참고 지표다. App Store 노출과 합산하지 않는다.
- 한 번에 개선 하나만 실행한다. 변경일과 비교 기간을 기록하고 결과를 본 뒤 다음 항목을 고른다.
- 스토어 노출 100회 미만이면 노출 확대가 충분히 실행됐는지부터 본다. 100회 이상에서 다운로드 5건 이상이면 같은 방법을 한 번 더 시도하고, 미달이면 유입 경로와 스토어 소개를 점검해 다음 개선 하나를 고른다. 작은 표본이므로 한 번의 달성으로 효과를 확정하지 않는다.
- 수집되지 않은 데이터는 0으로 처리하지 않는다. 본인·설정 테스트 접속은 구분해서 본다.

## SEO와 AI 검색 적용 원칙

Google의 AI Overviews·AI Mode는 일반 SEO 기본 원칙을 공유하며, 별도의 특수 최적화나 전용 스키마가 필수는 아니다. 우선 색인 가능 여부, 본문에 드러나는 정확한 기능 설명, 내부 링크를 정리한다. 이 원칙을 모든 AI 서비스의 정책으로 일반화하지 않고 다른 서비스는 실행 시 공식 문서를 확인한다. [Google AI 검색 안내](https://developers.google.com/search/docs/appearance/ai-features)

검색 제목은 페이지 내용을 구체적이고 간결하게 설명한다. 구조화 데이터는 본문과 일치하게 작성하며 특수 검색 표시를 보장하지 않는다. [검색 제목 안내](https://developers.google.com/search/docs/appearance/title-link), [앱 구조화 데이터 안내](https://developers.google.com/search/docs/appearance/structured-data/software-app)

### 2026년 11월 27일 G4 중간 관찰

Ddirori GA4 MCP에서 속성 ID를 지정해 Data API 보고서를 읽었다. 한국 시간 기준 11/16~17과 11/23~24의 월·화 이틀씩 비교했다. 배포일과 종료 후 48시간이 지나지 않은 날짜를 제외했다. 호스트는 `ddirori.com`과 `www.ddirori.com`, 국가는 전체다. 양쪽에서 세션 소스 `codex_setup`·`release_check`, 매체 `qa`·`internal_validation`, 캠페인 접두어 `studio_release_validation_`을 제외했다. 태그 없는 운영자 방문은 구별하기 어렵다.

스코어 경로는 `/score/`와 빌드에서 제공하는 주소 변형을 조회했다. 11/23은 호스트와 QA 조건을 풀어도 속성 전체의 이벤트 행이 반환되지 않았다. 빈 행은 집계 응답 상태로 기록했다. 스토어 노출·최초 다운로드는 이 조회에서 확인하지 못했다.

11/22에는 무료 음악수업 버튼도 홈 첫 화면에 추가됐다. 11/26의 [스코어 1.1.0 소개 반영](https://github.com/mann-lab-apps/ddirori/pull/6)과 [iPad PDF 사용 가이드](https://github.com/mann-lab-apps/ddirori/pull/7)는 이틀 중간 비교 이후이며, 예정된 6일 비교에는 포함된다. 버튼 하나의 효과를 분리하기에는 표본과 비교 조건이 부족하다.

다음 유입 실험 후보로 기존 Velog의 **띠로리 제작기 한 편**을 선택했다. 음악가 친구의 연습 불편을 다루고, 필기와 메트로놈 화면을 보여준다. 게시할 때는 [Velog 유입용 스코어 링크](https://ddirori.com/score/?utm_source=velog&utm_medium=referral&utm_campaign=score_build_log_01)를 사용한다. 6일 비교를 다시 조회한 뒤 게시 여부를 정한다.

### G4 6일 비교용 배포 전 기준값

2026-11-27 GA4 MCP 조회 기준으로 11/16~21 여섯 날짜 모두 운영 호스트에서 조회 행이 확인됐다. 같은 기간의 사이트 전체 조회수는 10회였고, 홈은 활성 사용자 9명·조회수 10회였다. 스코어 방문, App Store 이동 클릭, 홈을 직전 페이지로 하는 스코어 조회, 스코어로 시작한 세션은 모두 행이 없었다. 빈 행은 그대로 기록한다. 홈과 스코어의 경로 변형은 필터 안에서 한 번에 집계하므로 경로별 활성 사용자를 합산할 필요가 없다.

배포 후 11/23~28 기간은 집계 대기다. 12월 1일경 [저장한 GA4 MCP 요청](g4-ga4-requests.json)으로 양쪽 기간을 재조회한다. 각 요청의 `dimensions`와 `metrics`를 `common`과 함께 `run_report`에 전달한다. `dimension_filter`에는 `base_dimension_filter`를 쓰고, `extra_dimension_filters`가 있으면 공통 필터와 함께 `and_group.expressions`에 넣는다. 과거 이틀씩 두 구간을 넣어 날짜 범위별 조회가 작동하는 것을 확인했다.

날짜별 응답은 날짜가 해당 `dateRange`에 속하는 행만 사용한다. 두 날짜 범위를 요청하면 API가 상대 범위의 날짜에 0을 채운 행도 반환한다. 기간별 최종 비교에는 각 범위에 해당하는 집계 행만 사용하고, 표본 추출·잘림 여부와 실제 조회일을 함께 남긴다.

11/27에 [iPad PDF 악보 가이드](https://ddirori.com/score/guides/ipad-pdf/)에 받은 파일을 찾고 필기를 담은 PDF 사본을 공유하는 방법을 추가했다. 가이드의 검색 설명과 사이트맵 수정일도 맞췄다. 이 날짜는 G4 배포 후 비교 범위에 포함된다. 가이드의 검색 노출과 클릭은 Search Console에서 이 주소로 좁혀 관찰한다.
